# Терруар Чёрного моря

Сайт коллекции авторских вин и админка для управления его контентом.

Исходный проект был статическим лендингом на Astro, весь контент лежал массивами внутри компонентов. В этой ветке сайт переведён на серверный рендеринг, контент вынесен в SQLite, а поверх сделана админка на `/admin`.

## Быстрый старт

```bash
cp .env.example .env   # задайте ADMIN_LOGIN и ADMIN_PASSWORD (не короче 8 символов)
npm ci
npm run dev
```

- Сайт: http://localhost:4321
- Админка: http://localhost:4321/admin

При первом запуске база создаётся в `data/` и заполняется текущим контентом сайта, так что страница выглядит как раньше.

### Docker

```bash
docker compose up -d --build
```

Сайт откроется на http://localhost:8080. База и загруженные изображения лежат в volume `site-data` и переживают пересборку контейнера.

Без Docker тот же прод-сервер запускается так:

```bash
npm run build
npm start        # порт 8080; переменные ADMIN_LOGIN и ADMIN_PASSWORD должны быть в окружении
```

> Docker-образ при разработке локально не собирался (на машине не было Docker). Проверен прод-сервер, который в образе запускается той же командой: сборка без секретов, первый запуск с пустой базой, вход, CSRF, сжатие и заголовки, byte-range для видео.

### Проверки

```bash
npm run check   # типы и шаблоны Astro
npm test        # Vitest: валидация, вход и сессии, публикация контента, медиа, миграции, настройки
```

Тесты работают на временной базе и тестовых учётных данных, поэтому локальные `.env` и `data/` не затрагиваются.

## Что умеет админка

| Раздел | Возможности |
|---|---|
| **Вина** | Название, цена (пусто = «Цена по запросу»), стиль, привязка к терруару, фото бутылки, кадрирование, порядок, скрытие с сайта |
| **Терруары** | Название, slug, расположение, описание, фото и alt, **контур на карте**: рисуется кликами по карте или вводится JSON |
| **Журнал** | Фильмы, исследования, интервью: обложка, длительность, ссылка на материал (открывается в новой вкладке), порядок. Первый опубликованный материал становится крупной карточкой |
| **Настройки** | Заголовок и манифест главного экрана, блок «Где купить», e-mail и соцсети в подвале, title и description для поисковиков, картинка превью ссылки (og:image) для мессенджеров и соцсетей. Пока поле не редактировали, на сайте исходный текст |

Изменения видны на сайте сразу после сохранения, пересборка не нужна.

Что изменилось на публичной странице:
- кнопки-фильтры вин и кнопки на карте строятся из терруаров, а не захардкожены. Новый терруар автоматически появляется в фильтре, на карте и в карточках;
- у скрытого терруара вместе с ним скрываются и его вина.

## Архитектура

```
src/lib/db.ts          SQLite (встроенный node:sqlite), схема, миграции (PRAGMA user_version), транзакции
src/lib/settings.ts    описание редактируемых текстов: из него строятся форма, валидация и значения по умолчанию
src/lib/content.ts     схемы валидации (zod) и запросы к контенту
src/lib/media.ts       загрузка изображений: sharp → WebP 640/1280/1920 для srcset
src/lib/auth.ts        вход, сессии, ограничение попыток
src/lib/admin-form.ts  общая обработка форм админки: валидация, ошибки по полям, загрузка файла
src/lib/seed.ts        перенос исходного контента в базу при первом запуске
server.mjs             прод-сервер: обработчик Astro + сжатие (brotli/gzip) и заголовки безопасности
src/middleware.ts      защита /admin/*, no-store и noindex для админки
src/pages/admin/**     страницы админки (HTML-формы, работают без JS)
src/pages/media/*      раздача загруженных изображений с immutable-кешем
```

## Почему так

Я рассматривал три варианта:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Git-CMS (Decap / Sveltia) | Сайт остаётся статикой, история правок в git | Редакторам нужен GitHub, публикация ждёт CI-сборку (минуты) |
| Headless CMS (Directus / Strapi) | Готовый интерфейс, роли | Отдельный сервис с базой и обновлениями, избыточно для четырёх разделов |
| **SSR + SQLite + своя админка** ✅ | Один контейнер, мгновенная публикация, интерфейс под предметную область | Нужно поддерживать самим; один инстанс |

Для сайта такого размера выбран третий вариант:
- **SQLite через встроенный `node:sqlite`:** без отдельного сервера базы и без нативных зависимостей. Данные — один файл в volume.
- **SSR вместо пересборки статики:** правка видна сразу. SQLite работает в том же процессе, поэтому рендер страницы с запросом к базе занимает миллисекунды.
- **HTML-формы без фронтенд-фреймворка:** проще, работают без JS, так же устроен и сам сайт. JS только улучшает формы: редактор контура на карте, превью фото до загрузки, предупреждение о несохранённых изменениях.
- **Нарезка изображений при загрузке:** сайт раньше отдавал WebP через `astro:assets` на этапе сборки. Загруженные в рантайме фото нарезаются так же, через sharp, чтобы не потерять в производительности.

## Безопасность

- Логин и пароль задаются через `astro:env` как `secret`. Они читаются в рантайме и не вшиваются в сборку. Сравнение идёт за постоянное время.
- Сессионный токен: 256 бит, cookie `httpOnly` + `SameSite=Lax`, `Secure` при работе по HTTPS, срок жизни 12 часов. В базе хранится только SHA-256 токена. После смены пароля в `.env` все сессии сбрасываются при перезапуске: в базе лежит солёный scrypt-хэш учётных данных, и при несовпадении сессии удаляются.
- Не больше 5 неудачных попыток входа за 15 минут с одного IP.
- CSRF: встроенная проверка `Origin` в Astro для всех POST-запросов.
- Загрузки: принимаются только изображения до 15 МБ. При замене фото или удалении записи файлы удаляются, если на картинку больше никто не ссылается. Если сохранение упало, свежая загрузка тоже удаляется. Файл перекодируется через sharp, поэтому исходник никогда не отдаётся как есть. Имена файлов на выдаче проверяются по строгому шаблону (UUID).
- Заголовки на всех ответах, включая статику: `X-Content-Type-Options: nosniff`, `Referrer-Policy`, запрет встраивания сайта в чужие фреймы (`X-Frame-Options` + CSP `frame-ancestors`). Раньше их выставлял nginx; теперь это делает `server.mjs`.
- Админка отдаётся с `Cache-Control: no-store`, `X-Robots-Tag: noindex` и `frame-ancestors 'none'`: её нельзя встроить во фрейм, даже с самого сайта (защита от кликджекинга).
- HSTS нужно включать на том, кто терминирует TLS (reverse proxy или балансировщик), поэтому в приложении его нет.

## Ограничения и что дальше

- Одна учётная запись, без ролей. Следующий шаг — таблица пользователей с хэшами паролей (argon2) и ролями «редактор / администратор».
- Лимит попыток входа хранится в памяти, этого достаточно для одного инстанса. За reverse proxy нужно брать IP из `X-Forwarded-For`.
- Если форма не прошла валидацию, выбранный файл приходится выбирать заново (ограничение `<input type="file">`).
- Семь факторов терруара и подписи секций пока в коде. Их можно добавить в «Настройки» одной записью в `SETTINGS_GROUPS` (`src/lib/settings.ts`): форма и валидация строятся по этому описанию.
- Для продакшена: бэкап volume (`sqlite3 site.db ".backup ..."`), свой тайл-сервер или провайдер вместо `tile.openstreetmap.org`, журнал изменений (кто и что правил).
- E2E-тест (Playwright) на сценарий «вход → правка → изменение на сайте»; сейчас покрыта серверная логика.

## Найдено при тестировании

- Карта в редакторе контура перекрывала липкую шапку админки: Leaflet выставляет слоям `z-index` до 1000. Исправлено через `isolation: isolate` на контейнере карты.
- Загрузка картинки падала, если к базе ещё никто не обращался: папка `uploads/` создавалась только при открытии базы. В приложении это маскировал seed на первом запросе; тест на медиа поймал. Теперь `saveImage` сам создаёт папку.
- При переходе с nginx на Node потерялись сжатие и заголовки безопасности из `nginx.conf`: JS и CSS отдавались несжатыми (231 КБ вместо 63 КБ), админку можно было встроить в iframe. Вернул и то и другое в `server.mjs`.
